\chapter{Architettura e Design del Sistema}
\label{cha:architettura_e_design_del_sistema}
In questo capitolo vengono illustrate in dettaglio le scelte architetturali, le tecnologie adottate e i principi di design che guidano lo sviluppo del sistema DietiEstates. L'obiettivo è fornire una visione chiara della struttura software, giustificando le decisioni prese in ottica di manutenibilità, scalabilità e robustezza, secondo le migliori pratiche dell'ingegneria del software.

\section{Architettura del Sistema}
\label{sec:architettura_del_sistema}
Il sistema è stato progettato seguendo un'architettura multi-tier, specificamente un'architettura a tre livelli, che separa nettamente la logica di presentazione, la logica di business e la gestione dei dati. Questo approccio favorisce la modularità, il disaccoppiamento tra i componenti e la possibilità di sviluppare, manutenere e scalare i singoli livelli in modo indipendente.

\subsection{Livello di Presentazione (Presentation Tier)}
Il livello di presentazione è costituito da un'applicazione web di tipo Single-Page Application (SPA), sviluppata con il framework \textbf{Angular}. Questa applicazione viene eseguita interamente nel browser dell'utente e ha la responsabilità di renderizzare l'interfaccia grafica, gestire le interazioni dell'utente e comunicare con il livello di business tramite chiamate API. La scelta di una SPA permette di offrire un'esperienza utente fluida e reattiva, simile a quella di un'applicazione desktop, minimizzando i tempi di attesa grazie al caricamento asincrono dei dati.

\subsection{Livello di Business (Application Tier)}
Il cuore del sistema risiede nel livello di business, un'applicazione backend sviluppata in Java utilizzando il framework Spring Boot. Questo livello espone un'interfaccia RESTful API sicura, attraverso la quale il client può accedere alle funzionalità del sistema. Le responsabilità di questo tier includono:
\begin{itemize}
    \item \textbf{Gestione della Logica di Business:} Implementazione di tutte le logiche applicative, come la gestione degli annunci immobiliari, la gestione degli utenti e dei loro ruoli.
    \item \textbf{Autenticazione e Autorizzazione:} messa in sicurezza degli endpoint dell'API tramite Spring Security, gestendo l'autenticazione degli utenti (login) e l'autorizzazione basata sui ruoli (utente, agente, amministratore).
    \item \textbf{Comunicazione con il Livello Dati:} Interazione con il database PostgreSQL per il salvataggio e il recupero persistente delle informazioni.
    \item \textbf{Invio e Test Email (sviluppo):} in ambiente di development l'applicazione invia i messaggi SMTP verso il servizio \textit{MailDev}, che intercetta e rende disponibili le email su un'interfaccia web locale senza recapito reale. Questo consente di verificare contenuti, link e template (es. attivazione account, reset/cambio password) in modo sicuro e ripetibile; in produzione può essere configurato un provider SMTP reale.
\end{itemize}

\subsection{Livello Dati (Data Tier)}
Il livello dati è responsabile della persistenza delle informazioni. È costituito da un database relazionale PostgreSQL che memorizza tutti i dati dell'applicazione, come le anagrafiche degli utenti, i dettagli degli immobili e le agenzie immobiliari con i loro agenti.

L'accesso a questo livello è gestito esclusivamente dall'Application Tier, che si avvale di un Object-Relational Mapper (ORM) come Hibernate, tramite l'astrazione offerta da Spring Data JPA. L'uso di un ORM astrae la complessità del linguaggio SQL, permettendo agli sviluppatori di interagire con il database attraverso oggetti Java (Entity), migliorando la manutenibilità e la portabilità del codice.

\subsection{Servizi Cloud di Infrastruttura (RDS, S3)}
Per l'ambiente di produzione, il sistema adotta servizi cloud gestiti per garantire disponibilità, sicurezza e scalabilità dei componenti di persistenza e storage. In particolare:
\begin{itemize}
    \item \textbf{Amazon RDS (PostgreSQL):} il database relazionale è eseguito su Amazon RDS, che offre alta disponibilità, backup automatizzati, aggiornamenti gestiti e funzionalità di monitoring, riducendo l'onere operativo e migliorando l'affidabilità del Data Tier.
    \item \textbf{Amazon S3:} lo storage delle immagini è affidato a Amazon S3, che gestisce in modo scalabile i contenuti binari (upload, versioning, politiche di accesso) mantenendo i metadati nel database applicativo. Questo approccio separa nettamente i contenuti statici dalla persistenza relazionale e si integra con i servizi del livello di business.
\end{itemize}

\subsection{Build del progetto}
Il processo di build e messa in esecuzione del backend è stato progettato per essere ripetibile, portabile e pronto al deploy in ambienti cloud come AWS EC2. La strategia adottata combina la build del pacchetto applicativo Java (JAR) tramite Maven con la containerizzazione tramite Docker, e l'orchestrazione locale tramite Docker Compose.

\paragraph{Motivazioni della containerizzazione}
L'uso di Docker per il backend abilita diversi benefici chiave:
\begin{itemize}
    \item \textbf{Replicabilità e coerenza:} l'immagine Docker incapsula runtime, dipendenze e configurazioni, eliminando il classico \textit{“funziona sul mio PC”}.
    \item \textbf{Portabilità:} la stessa immagine può essere eseguita in locale, su EC2 o in un cluster orchestrato, senza variazioni di ambiente.
    \item \textbf{Sicurezza e isolamento:} i container isolano processi e risorse; le configurazioni sensibili transitano via variabili d'ambiente e/o file esterni.
    \item \textbf{Scalabilità operativa:} deployment semplificati, aggiornamenti atomici (pull + restart), integrazione naturale con registri di immagini (es. Amazon ECR).
\end{itemize}

\paragraph{Script di avvio \texttt{startup.sh}}
Lo script \hi{startup.sh} automatizza le due fasi principali:
\begin{itemize}
    \item \textbf{Build Maven:} \texttt{mvn clean package -DskipTests} produce il JAR dell'app, ripulendo artefatti precedenti. L'opzione \texttt{-DskipTests} velocizza la build in contesti di sviluppo.
    \item \textbf{Avvio dei servizi:} \texttt{docker compose up -d --build --remove-orphans} costruisce l'immagine del backend a partire dal Dockerfile e avvia i servizi definiti in Compose in modalità detatched.
\end{itemize}
Questo consente, con un singolo comando, di ottenere un JAR aggiornato e un container backend pronto, affiancato dagli eventuali servizi di sviluppo.

\paragraph{Dockerfile del backend}
Il file \hi{Dockerfile} definisce come impacchettare l'app Spring Boot in un'immagine eseguibile:
\begin{itemize}
    \item \textbf{Base image:} \texttt{eclipse-temurin:21-jdk-alpine} fornisce OpenJDK 21 su Alpine Linux, riducendo dimensione e tempi di pull.
    \item \textbf{Build arg:} \texttt{ARG JAR\_FILE=target/DietiEstates25-Backend-App.jar} permette di parametrizzare il percorso del JAR (utile in CI).
    \item \textbf{Packaging:} \texttt{COPY \${JAR\_FILE} app.jar} inserisce il JAR nell'immagine in un path standard.
    \item \textbf{Networking:} \texttt{EXPOSE 8080} documenta la porta applicativa.
    \item \textbf{Entrypoint:} \texttt{ENTRYPOINT ["java", "-jar", "/app.jar"]} esegue l'app come processo principale del container.
\end{itemize}
Questa impostazione favorisce semplicità (un unico artefatto) e chiarezza operativa, con un runtime Java aggiornato e supportato.

\paragraph{Docker Compose per sviluppo}
Il file \hi{docker-compose.yml} orchestra i servizi utili allo sviluppo locale:
\begin{itemize}
    \item \textbf{\textit{mail-dev}:} servizio basato su \texttt{maildev/maildev}, espone interfaccia web su 1080 e SMTP su 1025 (mappato da \texttt{\${MAIL\_PORT}}). Consente di testare template email senza recapito reale.
    \item \textbf{\textit{dietiestates-backend}:} costruisce l'immagine dal Dockerfile, espone 8080, carica variabili da file \texttt{.env} e imposta \texttt{MAIL\_HOST=mail-dev} per puntare al servizio SMTP di sviluppo. \texttt{depends\_on} garantisce l'ordine di avvio.
    \item \textbf{Networking:} i servizi condividono la rete \texttt{dietiestates\_network} per la risoluzione DNS interna.
\end{itemize}

\section{Tecnologie Adottate}
\label{sec:tecnologie_adottate}
La selezione delle tecnologie è stata guidata da criteri di maturità, supporto della comunità, produttività e aderenza agli standard di mercato.

\subsection{Backend}
\begin{itemize}
    \item \textbf{Java:} Linguaggio di programmazione robusto, orientato agli oggetti e indipendente dalla piattaforma, ampiamente utilizzato per lo sviluppo di applicazioni enterprise complesse e performanti.
    \item \textbf{Spring Boot:} Framework che semplifica drasticamente lo sviluppo di applicazioni basate su Spring. È stato scelto per la sua capacità di auto-configurazione, la gestione integrata delle dipendenze e l'ecosistema completo che include moduli per la sicurezza (Spring Security), l'accesso ai dati (Spring Data JPA) e la creazione di API REST (Spring Web).
    \item \textbf{JPA/Hibernate:} Standard per la persistenza dei dati in Java. Hibernate, come implementazione JPA, gestisce la mappatura degli oggetti Java alle tabelle del database, semplificando le operazioni CRUD e le query complesse.
    \item \textbf{Maven:} Strumento di build automation e gestione delle dipendenze, utilizzato per definire la struttura del progetto, compilare il codice sorgente e gestire le librerie di terze parti.
    \item \textbf{Docker:} Piattaforma di containerizzazione utilizzata tramite Docker Compose per definire e orchestrare l'ambiente di sviluppo e produzione, garantendo coerenza e replicabilità tra le diverse macchine e semplificando il deployment.
\end{itemize}

\subsection{Frontend}
\begin{itemize}
	\item \textbf{Angular:} Framework client-side basato su TypeScript, sviluppato da Google. È stato scelto per la sua architettura a componenti, che promuove la riusabilità del codice, e per il suo potente sistema di dependency injection, che facilita la scrittura di codice modulare e testabile.

	\item \textbf{TypeScript:} Superset di JavaScript che introduce la tipizzazione statica. Il suo utilizzo migliora la robustezza del codice, previene errori comuni in fase di sviluppo e aumenta la manutenibilità a lungo termine del progetto.

	\item \textbf{OpenAPI Generator:} Strumento fondamentale per l'integrazione tra frontend e backend. A partire dalla specifica OpenAPI esposta dal backend, questo strumento genera automaticamente un client API TypeScript completo e type-safe. Questo approccio riduce drasticamente il rischio di disallineamenti e è un pilastro per lo sviluppo contract-first.
\end{itemize}

\subsection{Approfondimento: Sicurezza con Spring Security e OpenID Connect}

Oltre alle scelte architetturali di alto livello, sono stati adottati specifici pattern di progettazione e configurazioni di sicurezza avanzate per garantire la robustezza, la manutenibilità e la sicurezza del sistema.

Per garantire un elevato livello di sicurezza nell'accesso alle risorse del sistema, è stato adottato \textbf{Spring Security} in combinazione con il protocollo OpenID Connect (OIDC). Questa scelta consente di implementare un sistema di autenticazione e autorizzazione robusto e scalabile, sfruttando le funzionalità offerte da provider di identità esterni. Questo approccio presenta diversi vantaggi:
\begin{itemize}
    \item \textbf{Sicurezza Migliorata:} La gestione delle credenziali è affidata a un provider specializzato, riducendo il rischio di vulnerabilità legate alla gestione interna delle password.
    \item \textbf{Scalabilità:} L'utilizzo di un IdP esterno consente di scalare facilmente il sistema di autenticazione senza dover implementare soluzioni personalizzate.
    \item \textbf{Esperienza Utente Unificata:} Gli utenti possono utilizzare le stesse credenziali per accedere a più applicazioni, migliorando l'usabilità e riducendo la necessità di gestire più account.
\end{itemize}
L'implementazione di Spring Security con OIDC prevede la configurazione del client OIDC all'interno dell'applicazione Spring Boot, la definizione delle regole di accesso alle risorse protette e la gestione dei token di accesso per autorizzare le richieste API.

\gbox{Il design pattern Factory per la gestione dei vari providers}{red}{
	
	Per gestire l'autenticazione tramite provider esterni (es. Google) secondo i protocolli OAuth2 e OpenID Connect, è stato implementato il \textbf{Factory Pattern}. Questa scelta di design è cruciale per disaccoppiare la logica di gestione dell'autenticazione dalle implementazioni specifiche di ciascun provider.\\


	Il cuore di questo pattern è rappresentato dall'interfaccia \texttt{OAuth2UserInfo}, che definisce un contratto comune per l'estrazione degli attributi di un utente (come ID, nome, email) a prescindere dal provider. Per ogni provider supportato, viene creata una classe concreta (es. \texttt{GoogleOAuth2UserInfo}) che implementa questa interfaccia, sapendo come mappare la struttura dati, spesso eterogenea, restituita da quel provider.\\

	La classe \texttt{OAuth2UserInfoFactory} agisce come ``fabbrica'': il suo metodo principale riceve in input il nome del provider e la mappa di attributi dell'utente, e restituisce l'istanza della classe concreta appropriata. In questo modo, i servizi che gestiscono il processo di login (\texttt{CustomOAuth2UserService} e \texttt{CustomOidcUserService}) non devono contenere logica condizionale (if/else o switch) per i diversi provider. Essi interagiscono esclusivamente con l'astrazione \texttt{OAuth2UserInfo}, favorendo il riutilizzo del codice e rendendo il sistema facilmente estensibile: per supportare un nuovo provider, è sufficiente creare una nuova implementazione dell'interfaccia e aggiornare la factory, \textit{senza modificare i servizi esistenti}.
}

\gbox{Gestione della sicurezza con la Security Filter Chain}{green!75!black}{

	La sicurezza dell'applicazione backend è gestita da Spring Security attraverso una catena di filtri (\textbf{Security Filter Chain}). Questo approccio, che implementa il pattern Chain of Responsibility, permette di applicare una serie di controlli di sicurezza a ogni richiesta HTTP in arrivo.\\

	La configurazione, definita nella classe \texttt{SecurityFilterConfig}, stabilisce l'ordine e il comportamento di questi filtri. Le principali responsabilità configurate includono:
	\begin{itemize}
	    \item \textbf{Autorizzazione degli Endpoint:} Viene definita una politica di accesso granulare per i diversi percorsi dell'API.
	
	    \item \textbf{Gestione delle Sessioni:} L'applicazione è configurata per essere \textit{stateless}, ovvero non viene creata alcuna sessione utente sul server. Questa è una scelta fondamentale per le API RESTful, in quanto garantisce la scalabilità e semplifica il bilanciamento del carico. L'autenticazione di ogni richiesta è affidata a un token.
	
	    \item \textbf{Integrazione OIDC e OAuth2:} La catena è configurata per intercettare e gestire i flussi di login con provider esterni, delegando il processo ai servizi specifici come \texttt{CustomOidcUserService}.
	
	    \item \textbf{Filtri Personalizzati:} È stato inserito un filtro custom, \texttt{AuthFilter}, posizionato strategicamente all'interno della catena. Questo filtro ha il compito di ispezionare l'header \texttt{Authorization} di ogni richiesta, estrarre e validare il JSON Web Token (JWT) e, in caso di successo, popolare il \texttt{SecurityContext} di Spring. Questo passaggio è ciò che permette al resto dell'applicazione di identificare l'utente autenticato e i suoi ruoli per le successive richieste API.
	\end{itemize}
}

\gbox{Access token JWT e Refresh Tokens}{blue}{
Per garantire un'autenticazione sicura e scalabile, il sistema utilizza JSON Web Tokens (JWT) come access token per autorizzare le richieste API. I JWT sono token compatti e auto-contenuti che trasportano informazioni sull'utente e sui suoi privilegi in modo sicuro. Quando un utente effettua il login tramite OIDC, riceve un access token JWT che deve essere incluso nelle intestazioni delle richieste API per accedere alle risorse protette. Questo approccio consente di evitare la necessità di mantenere sessioni lato server, migliorando la scalabilità dell'applicazione.\\

Accanto agli access token, il sistema implementa anche l'uso di \textbf{refresh token}. I refresh token sono token a lunga durata che consentono agli utenti di ottenere nuovi access token senza dover effettuare nuovamente il login. Quando un access token scade, l'applicazione può utilizzare il refresh token per richiedere un nuovo access token all'IdP, migliorando l'esperienza utente e mantenendo la sicurezza delle sessioni.

\section{Design dell'Interfaccia Utente (UI)}
\label{sec:design_dell_interfaccia_utente_ui}
Il design dell'interfaccia utente è stato concepito per essere pulito, intuitivo e funzionale, con l'obiettivo di massimizzare l'usabilità per le diverse categorie di utenti (visitatori, clienti, agenti e amministratori).

\begin{itemize}
    \item \textbf{Approccio User-Centric:} Ogni elemento dell'interfaccia è stato pensato mettendo al centro le esigenze dell'utente. La navigazione è stata strutturata in modo logico e coerente, permettendo un facile accesso alle funzionalità principali come la ricerca di immobili, la gestione del proprio profilo e, per gli utenti privilegiati, la gestione degli annunci e degli agenti.

    \item \textbf{Coerenza Visiva e Riusabilità:} L'adozione di un'architettura a componenti, nativa in Angular, ha permesso di creare elementi riutilizzabili (es. le card degli annunci, i campi dei form, la navbar). Questo non solo accelera lo sviluppo, ma garantisce anche una forte coerenza visiva e comportamentale in tutta l'applicazione, rendendo l'esperienza utente più prevedibile e confortevole.

    \item \textbf{Responsive Design:} L'interfaccia è stata progettata con un approccio "mobile-first", garantendo che l'applicazione sia perfettamente fruibile su un'ampia gamma di dispositivi, dai desktop agli smartphone. L'utilizzo di tecniche CSS moderne come Flexbox e Grid consente al layout di adattarsi fluidamente alle diverse dimensioni dello schermo.

    \item \textbf{Feedback all'Utente:} Il sistema fornisce un feedback visivo costante per ogni azione intrapresa dall'utente. Indicatori di caricamento (spinner) durante le chiamate asincrone, messaggi di successo o di errore chiari e validazione contestuale dei form sono tutti elementi implementati per migliorare la comunicazione tra il sistema e l'utente, riducendo l'incertezza e migliorando la percezione di reattività dell'applicazione.
\end{itemize}

\info{Scelta dell'interfaccia utente}{L'ispirazione per il layout e l'esperienza utente è tratta dai principali portali immobiliari moderni, cercando di adottare convenzioni già familiari agli utenti per ridurre la curva di apprendimento.}

\section{Descrizione dello schema per la persistenza dei dati}

\subsection{Panoramica e vincoli generali}

Lo schema utilizza PostgreSQL come motore relazionale e sfrutta estensioni quali \texttt{postgis} per la gestione dei dati geografici. Le entità principali sono modellate tramite tabelle normalizzate con vincoli di integrità (PK, FK e UNIQUE) e check constraint per valori enumerati (es. classe energetica, tipo di operazione).

Sequenze dedicate gestiscono gli identificatori delle tabelle principali (users, role, listing, listing\_image, ecc.) per garantire integrità e comportamento prevedibile nelle operazioni di insert.

\subsection{Tabelle principali}

\begin{itemize}
	\item  \textbf{agencies}: rappresenta le agenzie immobiliari (id, nome, email, telefono).
	
	\item  \textbf{users}: anagrafica utenti con campi di stato (enabled, account\_locked), riferimento opzionale a \texttt{agency\_id} e controlli sul provider di autenticazione. Le associazioni many-to-many verso \textbf{role} sono gestite tramite la tabella di join \textbf{users\_roles}.
	
	\item \textbf{role}: definisce i ruoli applicativi (ROLE\_AGENT, ROLE\_ADMIN, ROLE\_ADMIN\_ASSISTANT) con vincolo di unicità sul nome.
	
	\item  \textbf{listing}: entità principale per gli annunci immobilari. Oltre agli attributi descrittivi include un campo spaziale \texttt{coordinate} di tipo \texttt{geometry(Point,4326)} per memorizzare la posizione geografica del bene.
	
	\item  \textbf{listing\_image}: immagini associate ad un annuncio (url, sort\_order, created\_at, listing\_id FK), utilizzata per gestire gallerie e miniature.
	
	\item  \textbf{refresh\_tokens} e \textbf{otp\_token}: tabelle per la gestione di token di autenticazione e OTP.
\end{itemize}

\subsection{Funzioni e logica lato database}
Nel file di schema sono presenti stored procedures/functions utili a incapsulare logiche di business che devono essere eseguite atomically lato DB:

\begin{itemize}
	\item \texttt{revoke\_agent(user\_id INTEGER)}: funzione PL/pgSQL che rimuove ruoli associati a un utente (es. \texttt{ROLE\_AGENT}, \texttt{ROLE\_ADMIN\_ASSISTANT}) e azzera il campo \texttt{agency\_id} dell'utente. Questo tipo di funzione è utile per eseguire operazioni di revoca in modo trasparente e coerente, mantenendo la storia delle modifiche tramite l'aggiornamento del campo \texttt{last\_modified\_date}.

    \item  \texttt{get\_listings\_by\_agent(p\_agent\_id INT)}: funzione che restituisce gli annunci associati a un agente, estraendo anche coordinate (lon/lat) e la URL della prima immagine come \texttt{thumbnail\_url}. Fornisce un'interfaccia semplice e performante per le API che devono elencare gli annunci di un agente.

    \item \texttt{search\_listings\_by\_filters}: funzione per la ricerca dinamica degli annunci con filtri opzionali, paginazione e conteggio totale dei risultati; include coordinate e URL della miniatura per supporto alla UI.
\end{itemize}

Queste funzioni permettono di centralizzare controlli e operazioni ripetute, riducendo la complessità delle transazioni lato applicazione e favorendo coerenza dei dati.

\subsection{Motivazione per l'adozione di PostGIS}
PostGIS estende PostgreSQL con tipi spaziali (\texttt{geometry}, \texttt{geography}) e una ricca collezione di funzioni spaziali per operazioni geometriche e geografiche (intersezioni, distanze, buffer, ecc.). Le motivazioni principali della scelta sono:

\begin{itemize}
	\item \textbf{Ricchezza funzionale}: PostGIS fornisce operatori come \texttt{ST\_DWithin}, \texttt{ST\_Distance}, \texttt{ST\_Transform} e funzioni per estrarre coordinate (\texttt{ST\_X}, \texttt{ST\_Y}), fondamentali per query di ricerca per prossimità e per visualizzazione su mappe.

	\item  \textbf{Performance e indicizzazione}: gli indici spaziali GIST consentono ricerche molto efficienti su grandi insiemi di punti; l'uso di un indice GIST su \texttt{listing(coordinate)} permette di limitare rapidamente il numero di geometrie candidate prima di calcolare distanze precise.
	
	\item  \textbf{Precisione geografica}: PostGIS supporta SRID standard (es. 4326) e tipi \texttt{geography} per calcoli sulla superficie terrestre che considerano la curvatura della Terra, utile quando le ricerche devono essere espresse in metri.
\end{itemize}

Per questi motivi PostGIS offre il miglior compromesso tra semplicità d'uso, portata funzionale e performance per le operazioni geospaziali richieste dal prodotto.

\subsection{Uso di PostGIS nelle query di ricerca per raggio}
Le ricerche ``vicino a una posizione'' sono implementate con le funzioni spaziali come mostrato nel seguente listato:

\begin{lstlisting}[language=SQL]
-- Punto di ricerca: lon/lat in WGS84
SELECT l.*, ST_X(l.coordinate) AS longitude, ST_Y(l.coordinate) AS latitude
FROM listing l
WHERE ST_DWithin(
    l.coordinate::geography,
    ST_SetSRID(ST_MakePoint(:lon, :lat), 4326)::geography,
    :radius_meters
);
\end{lstlisting}

Descrizione:
\begin{itemize}
	\item La conversione a \texttt{geography} consente di esprimere il raggio in metri con precisione geodetica.
	
	\item \texttt{ST\_DWithin} è efficiente quando è supportato da un indice spaziale; PostgreSQL usa l'indice GIST per escludere rapidamente le geometrie lontane.
\end{itemize}

Per ottenere distanza ordinata si può usare:

\begin{lstlisting}[language=SQL]
SELECT l.*, ST_Distance(
    l.coordinate::geography,
    ST_SetSRID(ST_MakePoint(:lon, :lat), 4326)::geography
FROM listing l
WHERE ST_DWithin(l.coordinate::geography, ST_SetSRID(ST_MakePoint(:lon,:lat),4326)::geography, :radius_meters)
ORDER BY distance_m ASC
LIMIT :limit OFFSET :offset;
\end{lstlisting}


\subsection{La gestione delle immagini}
La gestione delle immagini nel sistema segue il principio di separazione delle responsabilità: i contenuti binari (file immagine) sono memorizzati in uno storage oggetto scalabile (Amazon S3), mentre PostgreSQL conserva i metadati relazionali necessari per la gestione delle gallerie, l'ordinamento e i riferimenti agli annunci.

\paragraph{Schema e metadati}
La tabella dedicata \texttt{listing\_image} contiene i campi principali necessari:
\begin{itemize}
    \item \texttt{sort\_order} (int) per stabilire l'ordine nella galleria
    \item \texttt{url} (varchar) che punta all'oggetto S3
    \item \texttt{listing\_id} (FK verso \texttt{listing})
\end{itemize}
Questa separazione consente operazioni transazionali sui metadati e sfrutta S3 per la consegna efficiente dei contenuti.

\paragraph{Servizi e configurazione}
La connettività con S3 è incapsulata in una classe di configurazione (vedi \texttt{S3Config.java}) e in un servizio applicativo che implementa l'interfaccia \texttt{ImageStorageService} (implementazione fornita da \texttt{S3ImageStorageService}). Il servizio si occupa di:

\begin{itemize}
    \item Validare il file (MIME type, dimensione, magic bytes) tramite \texttt{isValidImage}.
    \item Generare chiavi oggetto sicure e prevedibili (es. \texttt{listings/{listingId}/{uuid}.{ext}}) con \texttt{buildObjectKey}.
    \item Caricare oggetti su S3 (\texttt{putObject}) e restituire URL/chiave.
\end{itemize}

RETURNS VOID AS $$
BEGIN
    DELETE FROM users_roles
    WHERE users_id = user_id_in
    AND roles_id IN (SELECT id FROM role WHERE name IN ('ROLE_AGENT', 'ROLE_ADMIN_ASSISTANT'));

    UPDATE users
    SET agency_id = NULL, last_modified_date = NOW()
    WHERE id = user_id_in;
END;

-- Ricerca annunci con filtri dinamici, paginazione e conteggio totale
CREATE OR REPLACE FUNCTION search_listings_by_filters(
    op              TEXT DEFAULT NULL,
    ec              TEXT DEFAULT NULL,
    min_price       NUMERIC DEFAULT NULL,
    max_price       NUMERIC DEFAULT NULL,
    min_rooms       INT DEFAULT NULL,
    max_rooms       INT DEFAULT NULL,
    min_area        DOUBLE PRECISION DEFAULT NULL,
    max_area        DOUBLE PRECISION DEFAULT NULL,
    lng             DOUBLE PRECISION DEFAULT NULL,
    lat             DOUBLE PRECISION DEFAULT NULL,
    radius_km       DOUBLE PRECISION DEFAULT NULL,
    limit_rows      INT DEFAULT 20,
    offset_rows     BIGINT DEFAULT 0
)
RETURNS TABLE (
    listing_id      INT,
    title           VARCHAR,
    description     TEXT,
    address         VARCHAR,
    rooms           INT,
    bathrooms       INT,
    price           NUMERIC(38,2),
    area            DOUBLE PRECISION,
    energy_class    VARCHAR,
    lng_out         DOUBLE PRECISION,
    lat_out         DOUBLE PRECISION,
    thumbnail_url   VARCHAR,
    listing_operation VARCHAR,
    total_count     BIGINT
)
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
    where_sql   TEXT := ' WHERE 1=1';
    base_sql    TEXT := ' FROM listing l';
    count_sql   TEXT;
    query_sql   TEXT;
    total       BIGINT := 0;
BEGIN
    -- Filtri dinamici
    IF op IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.listing_operation = %L', op);
    END IF;

    IF ec IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.energy_class = %L', ec);
    END IF;

    IF min_price IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.price >= %L::numeric', min_price);
    END IF;

    IF max_price IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.price <= %L::numeric', max_price);
    END IF;

    IF min_rooms IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.rooms >= %L::int', min_rooms);
    END IF;

    IF max_rooms IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.rooms <= %L::int', max_rooms);
    END IF;

    IF min_area IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.area >= %L::double precision', min_area);
    END IF;

    IF max_area IS NOT NULL THEN
        where_sql := where_sql || format(' AND l.area <= %L::double precision', max_area);
    END IF;

    IF lng IS NOT NULL AND lat IS NOT NULL AND radius_km IS NOT NULL THEN
        where_sql := where_sql || format(
            ' AND ST_DWithin(l.coordinate::geography, ST_SetSRID(ST_MakePoint(%L, %L), 4326)::geography, %L::double precision * 1000)',
            lng, lat, radius_km
        );
    END IF;

    -- Conteggio totale dei risultati
    count_sql := 'SELECT count(*) ' || base_sql || where_sql;
    EXECUTE count_sql INTO total;

    query_sql := '
        SELECT
            l.listing_id,
            l.title,
            l.description,
            l.address,
            l.rooms,
            l.bathrooms,
            l.price,
            l.area,
            l.energy_class,
            ST_X(l.coordinate) AS lng_out,
            ST_Y(l.coordinate) AS lat_out,
            (
                SELECT li.url
                FROM listing_image li
                WHERE li.listing_id = l.listing_id
                ORDER BY COALESCE(li.sort_order, 0) ASC
                LIMIT 1
            ) AS thumbnail_url,
            l.listing_operation,
            ' || total || '::bigint AS total_count
        ' || base_sql || where_sql || '
        ORDER BY l.listing_id DESC
        LIMIT ' || limit_rows || ' OFFSET ' || offset_rows;

    RETURN QUERY EXECUTE query_sql;
END;
$$;

\section{Diagramma delle classi di design}
In questa sezione si documenta la struttura delle classi e dei moduli del backend. Il sistema è organizzato come un monolite modulare strutturato secondo principi DDD (\textbf{Domain-Driven Design}): ciascun package rappresenta un bounded context con responsabilità chiare ed è composto da:

\begin{itemize}
    \item \textbf{Domain model}: le classi che codificano le entità di dominio (DAO/Entity).
    \item \textbf{Repository/DAO}: astrazioni per la persistenza (Spring Data Repository o implementazioni custom).
    \item \textbf{Service/Application}: logica applicativa, orchestrazione di repository ed integrazione esterna.
    \item \textbf{Controller / API layer}: punti di ingresso HTTP/REST.
    \item \textbf{DTO / Mapper}: oggetti di trasferimento e trasformazioni tra API e classi di dominio.
\end{itemize}

Questa separazione facilita testabilità, responsabilità chiare e limiti per l'evoluzione del sistema.
